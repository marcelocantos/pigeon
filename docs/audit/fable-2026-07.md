## Architecture (as mapped during the audit)

Pigeon is a WebTransport/QUIC relay library plus an end-to-end-encryption stack, with the security-critical crypto and protocol logic implemented once in C (libpigeon, c/src/*.c) and reached from Go via cgo (cwire/), and mirrored into Swift/Kotlin/TS/TLA+ by a YAML-driven code generator (protocol/, cmd/protogen). The relay itself (cmd/pigeon/main.go + webtransport.go + quicserver.go + session.go) is a pure byte-shoveler: backends "register" and get an instance ID, clients "connect:<id>", and the relay bridges their two QUIC/WebTransport pipes opaquely (streams + datagrams) with no visibility into plaintext. Two listener stacks (WebTransport-over-HTTP3 and raw QUIC ALPN "pigeon") share one hub (session.go). A greeting on the primary stream (DecodeRelayGreeting) selects the role.

Client connectivity lives in the root package. pigeon.Register / pigeon.Connect (api.go) build a *Session over a *transport (transport.go, which adapts either quic-go or webtransport-go). Under the "remote-Listen L1" model, the backend holds one register control connection plus a pool of parked listen connections (listenPoolSize=4); the relay matches each arriving client to a parked listen and bridges end-to-end, so every Session owns its own QUIC connection. Activation (auth_request/auth_ok) and the pairing ceremony (hello/welcome/confirm) both run inside libpigeon, driven over a cgo GoTransport adapter (cgo_transport.go, cwire/gotransport.go). The Session exposes named reliable streams (OpenStream/AcceptStream) and pre-declared datagram channels, all AEAD-protected by a single cwire.Channel.

Threading/concurrency model: the relay spawns one goroutine per registered instance (blocked on ctx.Done for lifetime tracking) and, per bridged client, a fan of goroutines in bridge() — two primary-stream pumps, two datagram pumps, two stream-accept loops, and two goroutines per accepted sub-stream — coordinated by a sync.WaitGroup, an errCh, a streamTracker, and context cancellation. On the client side each Session runs an acceptLoop (sub-stream demux) and a datagramLoop, plus per-call Recv goroutines. The crypto Channel is meant to be shared across all of a session's stream and datagram pumps concurrently. Instance lifecycle is a context tree: instance ctx derives from the register connection's ctx; bridge ctx derives from the client's; Session ctx derives from the caller's.

Crypto construction: X25519 ECDH → HKDF-SHA256 (empty salt, direction-label info strings) → AES-256-GCM. The nonce is the 8-byte little-endian message sequence counter zero-padded to 12 bytes, with the same 8 bytes prepended to the ciphertext and used as GCM AAD. Session keys are derived deterministically from the persisted PairingRecord (static X25519 keys) with fixed info strings; the counter starts at zero on every new channel. A 6-digit SAS confirmation code (HKDF over the two sorted ephemeral pubkeys, mod 10^6) provides MitM detection during pairing.

## Load-bearing invariants

- AES-GCM nonce uniqueness per key: every (key, nonce) pair must be used at most once. VIOLATED three ways — (a) session keys are a deterministic function of the static PairingRecord with fixed HKDF info and no per-session salt, and each new channel resets send_seq to 0, so every reconnect reuses nonce 0,1,2... under the identical key; (b) two concurrent Sessions under one PairingRecord derive identical keys and both start at 0; (c) the production cwire.Channel increments send_seq with a non-atomic C `send_seq++` under no Go lock while api.go shares one channel across all stream/datagram senders, so concurrent Send can hand two messages the same nonce.
- Bullseye T44.1: concurrent sessions under one PairingRecord must derive DISTINCT keys. VIOLATED — cwire.DeriveSessionChannel and crypto.PairingRecord.DeriveChannel take no session nonce/salt; keys depend only on the record and a fixed direction label.
- Relay routing integrity: an instance ID maps to exactly one owning backend, a register must not silently displace a live instance, and unregister must only remove the entry owned by the departing connection. VIOLATED — hub.register does last-writer-wins map assignment on a client-chosen greeting ID, and hub.unregister deletes/cancels whatever is currently mapped to that ID regardless of which connection owns it (session.go).
- A single AEAD channel in ModeStrict must only carry a single in-order delivery path. VIOLATED at the Go Session layer — api.go routes every named stream AND every datagram through one cwire.Channel derived in "stream" (strict) mode with one shared recv_seq; multiplexed streams and inherently-lossy datagrams cannot satisfy a single strict global counter, so legitimate traffic is rejected once more than one stream or any datagram loss occurs.
- The state-machine executor rejects illegal transitions and authentication requires a completed pairing. Partially holds: protocol/machine.go and the generated executors reject unmatched (state,msg) pairs, and channel keys come from the pairing-derived ECDH so an unpaired peer cannot produce valid ciphertext. But runtime activation (c/src/activation.c) authenticates only a plaintext device_id with no challenge/nonce/signature, while the generated SessionMachine models a received_auth_nonce and crypto.Identity exposes an unused Sign — a fidelity gap between the TLA+/generated model and the executor.
- Confirmation code must bind the actual ECDH keys used, so a substituted key yields a different code. Holds — both C and Go derive it over the two ephemeral pubkeys, order-independent; MitM substitution changes each side's code.
- Framed reads must be bounded (maxMessageSize) to prevent unbounded allocation. Holds for per-message size, but there is NO cap on the number of registered instances, parked listens, bridged sessions, or per-bridge goroutines/streams — resource growth is unbounded under a hostile peer.
- cgo lifetime: a GoTransportRef/confirmHandle must outlive every session copying its vtable and be released exactly once; stream handle map entries (cgo_transport.go streamHandles) must be freed on close. Mostly holds via explicit Close/removeStream, but leaks are possible on abnormal teardown paths.

## Trust boundaries

- Relay greeting from any peer: DecodeRelayGreeting output (Variant, InstanceId, Token) in webtransport.go handlePigeon and quicserver.go handleConnection — the InstanceId is attacker-chosen and used directly as the hub map key (register can claim/overwrite arbitrary IDs). Note WT handleConnect does NOT length-validate instanceID while QUIC handleConnect enforces len<=64.
- Bearer token comparison in auth.go BearerTokenAuth (constant-time via subtle.ConstantTimeCompare — OK); but the default relay is open (no token) and WebTransport CheckOrigin unconditionally returns true, so any origin/any peer can register on the default config.
- Client-side TLS to the relay defaults to InsecureSkipVerify=true in api.go (Register/Connect) and pairing/pairing.go — the relay's identity is not verified, enabling relay impersonation and bearer-token capture by an active network attacker (payload confidentiality still rests on E2E crypto).
- Peer JSON pairing messages parsed by a hand-rolled C parser: c/src/pairing.c json_find_string_field / b64_decode / json builders operating on peer-controlled hello/welcome/confirm frames (fixed-size stack buffers; check bounds carefully).
- Peer activation frames decoded by c/src/activation.c uvarint/auth_request/auth_ok decoders (attacker-controlled device_id and reason strings).
- Peer public keys fed to X25519: crypto.go DeriveSessionKey, identity.go DeriveSharedSecret, and c/src/crypto.c crypto_scalarmult — low-order/all-zero shared secret is rejected by Go stdlib and libsodium return codes, so verify every caller checks the error.
- Persisted PairingRecord and file identity loaded from disk/JSON: crypto.UnmarshalPairingRecord, PairingRecord.DeriveChannel, and identity.go NewFileIdentity/decodeFileIdentity (key-length validation present at decode).
- Relayed stream/datagram payloads: bridged opaquely by session.go bridge/bridgeStream with no validation (by design) — but the primary-stream pumps forward frames without honoring maxMessageSize on the relay path, and there is no per-connection resource ceiling.
- cgo boundary: unsafe.Pointer stream handles round-tripped through C (cwire/gotransport.go trampolines, cgo_transport.go streamHandles map) and length-checked copies between C buffers and Go slices.

## Strategic recommendations

PRINCIPAL-ENGINEER BRIEFING — pigeon reliability review

The single confirmed finding (SAS grind) is not an isolated bug; it is the visible tip of a systemic pattern where the *specification/model* asserts a security property that the *deployed implementation* cannot uphold. Before another engineer touches this code, they need to understand three cross-cutting risk clusters.

1. MODEL-vs-IMPLEMENTATION FIDELITY IS THE DOMINANT SYSTEMIC RISK.
The whole value proposition of this repo — "crypto/protocol implemented once, mirrored to Swift/Kotlin/TS/TLA+ via YAML codegen" — creates a false sense of assurance because the TLA+/generated model abstracts away the exact quantities that make the C implementation exploitable. The confirmed SAS finding is the archetype: MitMDetectedByCodeMismatch (pairing.yaml) proves detection using an *injective* symbolic DeriveCode (returns the sorted key pair, no truncation, no attacker-chosen input), while the shipped code truncates to ~20 bits over attacker-controllable ephemerals with no commitment round. The model is "green" and the product is broken. The same fidelity gap recurs in the activation invariant: the generated SessionMachine models received_auth_nonce and crypto.Identity exposes a Sign method, but c/src/activation.c authenticates a bare plaintext device_id with no challenge/nonce/signature — the executor is strictly weaker than the model it claims to implement. RECOMMENDATION: treat every TLA+ property as a *contract the C must honour with matching concrete parameters*, and add abstraction-fidelity review to the codegen pipeline. Any property whose model operator is more idealized than the C primitive (truncation, bit-width, attacker input ordering) must be flagged. Do not let "TLA+ says it's safe" close a crypto ticket.

2. AES-GCM NONCE UNIQUENESS IS VIOLATED STRUCTURALLY, IN THREE INDEPENDENT WAYS — THIS IS A CATASTROPHIC-CLASS INVARIANT AND SHOULD BE THE #1 REMEDIATION PRIORITY, ABOVE THE SAS FINDING IN BLAST RADIUS. (It appears in the invariant list rather than the finding list, but the architecture notes assert it as VIOLATED and it deserves top billing in the fix plan.) The keys are a deterministic function of the static PairingRecord with fixed HKDF info and no per-session salt, and send_seq resets to 0 on every new channel — so every reconnect replays nonce 0,1,2… under an identical key (nonce reuse in GCM leaks XOR of plaintexts and, worse, enables forgery via authentication-key recovery). This compounds with the T44.1 violation (concurrent sessions under one PairingRecord derive identical keys, both starting at 0) and a *data-race* nonce collision (non-atomic C send_seq++ with no Go lock while api.go fans one shared cwire.Channel across all stream and datagram senders). Root cause is a single missing design element: there is no per-session/per-channel key-diversifier. RECOMMENDATION: inject a fresh random per-session salt (or ephemeral-ECDH rekey) into HKDF so DeriveSessionChannel/DeriveChannel produce distinct keys per session, and make sequence advancement atomic and serialized at the Go boundary. This one change closes T44.1 and two of the three nonce-reuse vectors at once (see DEDUP).

3. THE STRICT-CHANNEL / MULTIPLEXING CONTRADICTION IS A LIVENESS/CORRECTNESS TIME BOMB, NOT JUST A ROBUSTNESS NIT. The invariant "a single AEAD channel in ModeStrict carries a single in-order path" is violated at the Session layer: api.go routes every named stream AND every lossy datagram through one strict channel with one shared recv_seq. This is self-inflicted — under normal, non-adversarial use, the second concurrent stream or the first dropped datagram makes the shared counter diverge and legitimate traffic is rejected. It means the shipping configuration cannot actually be exercised at its advertised concurrency, which also explains why the nonce-reuse and race issues may not have surfaced in testing: the product may only ever have been tested single-stream, no-loss. RECOMMENDATION: per-stream and per-datagram-channel counters/sub-keys, or a documented single-path restriction. Fixing this is a prerequisite for any realistic load/soak testing that would expose cluster 2.

4. THE RELAY TRUSTS ATTACKER-CHOSEN IDENTIFIERS AND HAS NO RESOURCE CEILING. Routing integrity is violated three ways in session.go: hub.register does last-writer-wins on a client-chosen greeting InstanceId (any peer can claim/overwrite a live instance ID — a trivial takeover/DoS), and hub.unregister deletes/cancels whatever is mapped to that ID regardless of ownership (any peer can evict any instance). Compounding: WT handleConnect does NOT length-validate instanceID while QUIC enforces len<=64 — an inconsistent trust boundary across the two listener stacks that share one hub, which is exactly where authors introduce bugs. And there is no cap on registered instances, parked listens, bridged sessions, or per-bridge goroutines/streams, so the per-instance-goroutine + per-bridge-goroutine-fan model (WaitGroup/errCh/streamTracker) is an unbounded memory/goroutine amplifier under a hostile peer. The relay path also forwards primary-stream frames without honoring maxMessageSize. RECOMMENDATION: bind instance ownership to the registering connection (register must not displace a live instance; unregister must match the owning connection), unify length validation across both listeners, and impose per-connection and global ceilings.

5. TRANSPORT-LAYER TRUST DEFAULTS UNDERMINE THE E2E STORY. InsecureSkipVerify=true is the default in api.go (Register/Connect) and pairing/pairing.go, the default relay is open (no bearer token), and WebTransport CheckOrigin unconditionally returns true. Individually defensible ("E2E crypto protects payloads"), but collectively they are the *enabling precondition* for the confirmed SAS attack (relay impersonation splits the pairing pipe) and for bearer-token capture. The constant-time token compare in auth.go is good hygiene that is moot when the default config ships no token and no relay-identity verification. RECOMMENDATION: pin the relay's TLS identity (or make verification opt-out, not opt-in) and re-evaluate the "E2E makes transport trust irrelevant" assumption in light of cluster 1 — the pairing channel is where transport trust and crypto trust are coupled.

CROSS-CUTTING THEME FOR THE FIXER: pigeon's failures concentrate at the *seams* — model↔C, C↔Go (cgo/nonce/atomicity), WT-listener↔QUIC-listener, transport-trust↔crypto-trust, single-channel↔multiplexed-usage. The primitives in isolation are largely correct (SAS binds the right keys order-independently; low-order X25519 points are rejected; framed reads are per-message bounded; constant-time token compare). The defects live in the composition. Prioritize: (1) per-session key diversification + atomic sequencing [closes T44.1 + two nonce vectors], (2) SAS commitment round + identity binding, (3) relay ownership/quotas, (4) strict-channel multiplexing redesign, (5) transport-trust defaults + activation challenge-response to match the model.

### F1 — [CRITICAL] Shared cwire.Channel send_seq/recv_seq mutated with no lock across concurrent Stream/Datagram senders → data race and AES-GCM nonce reuse

- **Location:** `c/src/crypto.c:160`
- **Dimension:** -
- **Invariant violated:** AES-GCM (key,nonce) uniqueness: the per-session AEAD channel is shared across all stream pumps and the datagram pump (per crypto/channel_concurrency_test.go), so its sequence counter must be advanced atomically; every message must get a distinct nonce.
- **Failure scenario:** A Session (built by pigeon.Connect/Register in api.go) holds one *cwire.Channel in s.channel. Two goroutines send concurrently — e.g. stream A calls Stream.Send while stream B calls Stream.Send, or any stream Send races a Datagram.Send. Stream.Send (api.go:785) runs s.channel.Encrypt(msg) BEFORE taking s.sendMu (api.go:791), and each *Stream has its own sendMu; Datagram.Send (api.go:861) takes no lock at all. cwire.Channel.Encrypt (cwire/session.go:102) calls pigeon_channel_encrypt with no mutex, which executes the non-atomic read-modify-write `uint64_t seq = ch->send_seq++;`. Goroutine A and B both read send_seq==5, both build nonce = LE64(5) and both seal under the identical send_key, then each writes ciphertext prefixed with seq=5 on the wire. Result: two distinct plaintexts encrypted under the same (key, nonce=5) — a catastrophic AES-GCM break (recovers the GHASH auth key and XOR of the two plaintexts) — plus a genuine C-level data race on ch->send_seq. The strict-mode peer additionally rejects one of the two seq=5 frames (recv_seq mismatch), corrupting the stream. The receive side is symmetric: Stream.Recv's decrypt goroutine (api.go:814) and datagramLoop (api.go:719) both call s.channel.Decrypt concurrently, racing the non-atomic ch->recv_seq at crypto.c:195/217.
- **Evidence:**

```
c/src/crypto.c:160  `uint64_t seq = ch->send_seq++;`  (non-atomic RMW) — reached with no lock via cwire/session.go:102 `n := C.pigeon_channel_encrypt(ch.c, ...)`; shared by api.go:785 `ct, err := s.channel.Encrypt(msg)` (before sendMu at 791, per-stream mutex) and api.go:861 `ct, err := d.session.channel.Encrypt(plain)` (no lock). Contrast crypto/crypto.go: `sendSeq atomic.Uint64` / `c.recvMu.Lock()`.
```

- **Fix sketch:** Give cwire.Channel a sync.Mutex and take it in both Encrypt and Decrypt (cwire/session.go) so the C send_seq++/recv_seq updates are serialized; or, better, back the production Session's AEAD with crypto.Channel (already atomic sendSeq + recvMu, and proven safe by crypto/channel_concurrency_test.go) instead of the unguarded cwire.Channel. Independently, do not derive keys deterministically with a per-channel counter reset without a per-session salt, but the concurrency fix is the lock.
- **Verification:** The Go race detector will NOT see this (the racing write is in C). Instead add a functional test mirroring crypto/channel_concurrency_test.go but over an api.go Session (or directly over one *cwire.Channel): fan out N goroutines across two Streams plus a Datagram, capture the 8-byte LE seq prefix of every produced ciphertext, and assert all prefixes are distinct. Before the fix, duplicate prefixes appear (and a strict-mode Decrypt of the batch rejects some frames). After adding the mutex, all prefixes are unique and every frame decrypts. Optionally build the C with -fsanitize=thread to observe the ch->send_seq race directly.

### F2 — [CRITICAL] AES-GCM nonce reuse: session keys are a deterministic function of the static PairingRecord and every new channel resets the counter to 0 (T44.1)

- **Location:** `cwire/connect.go:355`
- **Dimension:** -
- **Invariant violated:** Every (AES-GCM key, nonce) pair must be used at most once. Concurrent/reconnecting sessions under one PairingRecord must derive DISTINCT keys (bullseye T44.1).
- **Failure scenario:** A client pairs once and persists a PairingRecord. It connects (activation mode): api.go:439 calls cwire.DeriveSessionChannel(record,false), which derives send_key=HKDF(X25519(localPriv,peerPub), info="client->backend") with an all-zero HKDF salt (c/src/crypto.c:36) and pigeon_channel_init sets send_seq=0 (c/src/crypto.c:121). It sends messages carrying GCM nonces 0,1,2,... . The client disconnects and later reconnects using the SAME record: DeriveSessionChannel recomputes the IDENTICAL send_key (no per-session salt/nonce input exists — the wire auth_request carries only a plaintext device_id, c/src/activation.c:66-84, so nothing session-specific feeds the KDF) and again starts at nonce 0. An eavesdropper (the untrusted relay, or a passive network attacker) who recorded both connections now holds two ciphertexts C1,C2 encrypted under the same (key,nonce=0): C1 XOR C2 = P1 XOR P2, leaking plaintext, and two messages under one GCM nonce also expose the GHASH authentication subkey, enabling forgery. The same collision occurs immediately (no reconnect needed) when the same device opens two concurrent sessions, or two devices share one record: both derive identical keys and both start at nonce 0.
- **Evidence:**

```
var sendInfo, recvInfo string
if isBackend { sendInfo, recvInfo = backendToClient, clientToBackend } else { sendInfo, recvInfo = clientToBackend, backendToClient }
... pigeon_derive_session_key(&cRec.local_private_key[0], &cRec.peer_public_key[0], sendInfoC, ...)   // no salt/nonce; deterministic in the static record
// c/src/crypto.c:121  ch->send_seq = 0;   // every new channel restarts nonces at 0
```

- **Fix sketch:** Inject a fresh, per-session random salt into key derivation. Exchange a random nonce during activation (the model already has received_auth_nonce, protocol/session_gen.go:450 — put it on the wire in auth_request/auth_ok) and feed both sides' contributions into the HKDF salt (or info), so DeriveSessionChannel takes a session nonce parameter and no two sessions derive the same key. Apply the same fix to the mirror public API crypto.PairingRecord.DeriveChannel (crypto/crypto.go:281) and crypto.DeriveSessionKey. Never rely on the counter reset alone for uniqueness.
- **Verification:** Before: in a Go test, call cwire.DeriveSessionChannel(rec,false) twice from one record, Encrypt distinct plaintexts P1,P2 on the two channels; assert the 8-byte seq prefixes are both 0 AND that xor(ct1[8:24],ct2[8:24]) == xor(P1[:16],P2[:16]) (proves identical keystream => nonce+key reuse). After: the two channels use different keys, so that xor identity no longer holds and the derived send_keys differ. Add a regression test asserting two channels from one record have unequal keystreams for seq 0.

### F3 — [HIGH] Reconnect authentication reaches SessionActive on a bare, public device_id — the model's secret/nonce authenticators are absent from the runtime wire format (no proof-of-pairing at the executor)

- **Location:** `c/src/activation.c:225`
- **Dimension:** -
- **Invariant violated:** AuthRequiresCompletedPairing (session.yaml:1307-1309): reaching backend SessionActive must require the peer to have completed pairing, i.e. prove possession of the pairing-derived secret/key — not merely assert a known device_id. The state machine must reject an activation from a peer that never paired.
- **Failure scenario:** Backend B has paired with client device D and runs pigeon.Register with a resolver that returns D's PairingRecord for device_id == D's InstanceID. That InstanceID is base64(sha256(D_xpub)[:16]) (crypto/identity.go:113-116) — a value transmitted in cleartext in the pairing hello/welcome and embedded in the QR token, so it is known to any pairing-time observer and is NOT a secret. Attacker A, holding no pairing key, dials the relay, gets bridged to B's parked listen, and as the very first bytes on the (still-unencrypted) primary stream sends the trivially hand-constructed frame pigeon_encode_auth_request(device_id=D) (activation.c:66-84 encodes only tag+len+id; no secret, nonce, challenge, or signature). pigeon_run_backend_activation decodes it, calls resolve(device_id=D) which returns known (activation.c:225), drives the SessionMachine Paired->AuthCheck->SessionActive, sends auth_ok (activation.c:259-268) and returns 0. In api.go activate() this yields result.Accepted==true (api.go:340), a channel is derived from D's record, and a *Session bound to DeviceID=D is returned with acceptLoop/datagramLoop goroutines started (api.go:357-363). The backend's activation state machine has therefore reached SessionActive for a peer that proved zero key possession. The AEAD channel still blocks plaintext read/write, but (a) application code that trusts the returned Session / "device D connected" before the first AEAD round-trip is spoofed, and (b) every forged auth commits a full Session + 2 goroutines with no authentication and no rate limit. The runtime auth_request omits the `secret` (device_secret) and `nonce` fields the model's auth_request specifies (session.yaml:648-655), and crypto.Identity.Sign (identity.go:130) — the only proof-of-possession primitive — has no runtime caller.
- **Evidence:**

```
// activation.c:224-234 — the entire backend authentication decision:
backend_auth_ctx auth_ctx;
auth_ctx.known = (resolve(resolve_userdata, device_id, out_record) == 0);
...
if (pigeon_backend_handle_message(machine, PIGEON_SESSION_MSG_AUTH_REQUEST) <= 0) { return -1; }
// activation.c:66-84 — auth_request carries ONLY device_id (no secret/nonce/sig):
int pigeon_encode_auth_request(const char *device_id, uint8_t *buf, size_t buf_len){ ... buf[0]=TAG_AUTH_REQUEST; ... memcpy(buf+off, device_id, id_len); ... }
// api.go:340 — Accepted trusted, Session built & goroutines spawned (357-363):
if !result.Accepted { ... }
```

- **Fix sketch:** Bind activation to actual key possession instead of a public identifier: derive the AEAD channel from the resolved PairingRecord FIRST and require the client's auth_request (or an immediate follow-up) to be AEAD-sealed/verified under that channel so a peer lacking the key cannot complete; and/or add a backend challenge nonce that the client must MAC/sign with the pairing-derived key (wire crypto.Identity.Sign or a channel MAC in). Populate and verify the `secret`/`nonce` fields the session.yaml model already specifies, and reject on mismatch before returning an Accepted Session.
- **Verification:** Before: add a Go test that stands up the pigeon.Register backend with a resolver returning a record for a known ID, then a raw client that writes only pigeon_encode_auth_request(knownID) with NO valid pairing key/channel, and assert Listener.activate returns an Accepted Session (bug reproduced); or unit-drive pigeon_run_backend_activation with a resolver returning known and observe it returns 0 despite the caller supplying no secret. After: the same forged/keyless auth_request must cause activate() (and pigeon_run_backend_activation) to return an error and never reach SessionActive.

### F4 — [HIGH] Confirmation-code SAS has no commitment round and only ~20 bits, so the relay MitM can grind the two displayed codes to match

- **Location:** `c/src/pairing.c:368`
- **Dimension:** -
- **Invariant violated:** The 6-digit confirmation code must let a human detect a man-in-the-middle: a relay that substitutes its own keys must be unable to make both sides display the same code.
- **Failure scenario:** The ceremony is hello -> welcome -> confirm with NO commit-then-reveal step (protocol/pairing.yaml lines 36-51). The initiator sends its ephemeral public key in the clear as the first message (c/src/pairing.c:366-368 build_hello/pair_send), and the code is HKDF(sorted eph pubkeys) mod 1000000 (c/src/crypto.c:103) = ~19.9 bits, computed over ephemerals only (identity_pub is decoded at pairing.c:276-281 but discarded — out_record stores only ephemeral keys, pairing.c:316-321). Because TLS to the relay defaults to InsecureSkipVerify, the relay (or an attacker impersonating it) can split the connection. Attack: (1) receive initiator's eph_I; (2) forward attacker key eph_M1 to the acceptor; (3) receive acceptor's eph_A; now target T = Code(eph_M1, eph_A) is fixed and known to the attacker; (4) brute-force ephemeral keypairs eph_M2 until Code(eph_I, eph_M2) == T — expected ~10^6 = 2^20 HKDF evals, well under a second; (5) send welcome{eph_M2} to the initiator. Both humans now see the identical code T and confirm, yet the attacker holds distinct ECDH secrets with each side and transparently relays/decrypts all subsequent traffic. The SAS provides no real MitM protection.
- **Evidence:**

```
// c/src/pairing.c:366-368 initiator reveals eph in the clear, no prior commitment
int hlen = build_hello(local_eph_pub, identity_pub, instance_id, buf, PIGEON_MAX_MSG);
if (pair_send(transport, stream, buf, (size_t)hlen) != 0) { ... }
// c/src/crypto.c:103  val %= 1000000;   // ~20-bit SAS over attacker-controllable ephemerals
// c/src/pairing.c:319-321 out_record keeps only ephemeral keys; identity_pub discarded
```

- **Fix sketch:** Add a commitment round so neither side can grind: the responder must send H(commit-salt || its eph_pub) BEFORE the initiator reveals eph_pub, and reveal eph_pub only after receiving the initiator's key (standard short-authenticated-string AKE, e.g. the ZRTP/PAKE pattern). Bind the long-term identity_pub into the SAS input as well so identity substitution is detected. Consider widening the SAS if commitment cannot be guaranteed. Modulo bias here is negligible; the exploitable weakness is the missing commitment plus small code space.
- **Verification:** Before: write a test that fixes eph_I, eph_M1, eph_A (via GenerateKeypair) and loops generating eph_M2 until pigeon_derive_confirmation_code(eph_I,eph_M2)==pigeon_derive_confirmation_code(eph_M1,eph_A); assert it succeeds within a few million iterations (demonstrates the grind). After the commitment fix: the attacker must commit to eph_M1 before seeing eph_A (and vice-versa), so no offline grind is possible; the test's precondition no longer holds.

### F15 — [LOW] AES key material is not zeroized when a channel is freed (C.free instead of sodium_memzero)

- **Location:** `cwire/session.go:83`
- **Dimension:** -
- **Invariant violated:** Secret key material should be wiped from memory as soon as it is no longer needed (defense in depth), not left in freed heap.
- **Failure scenario:** The production channel holds send_key[32]/recv_key[32] in cleartext inside the heap-allocated pigeon_channel (c/include/pigeon/pigeon.h struct). When the channel is finalized (cwire/session.go:80-85) or the session closes (cwire/session.go:201-212), the struct is released with plain C.free with no prior sodium_memzero, so the 256-bit AES keys linger in freed heap and can be recovered from a core dump, swap, or a later heap-spray read. DeriveSessionChannel also leaves the derived keys in the Go [32]C.uint8_t sendKey/recvKey arrays (cwire/connect.go:352-368) and in cRec un-wiped. Contrast the KDF internals, which do zeroize (hkdf_sha256 wipes prk, pigeon_derive_session_key wipes the shared secret) — the long-lived channel keys are the ones left behind.
- **Evidence:**

```
runtime.SetFinalizer(ch, func(ch *Channel) {
    if ch.c != nil {
        C.free(unsafe.Pointer(ch.c))   // frees send_key/recv_key without sodium_memzero
        ch.c = nil
    }
})
```

- **Fix sketch:** Call sodium_memzero(ch, sizeof(*ch)) (or at least over send_key/recv_key) immediately before C.free in the finalizer and in Session.Close; add a pigeon_channel_free helper in C that wipes then frees. Zero the transient sendKey/recvKey/cRec arrays in DeriveSessionChannel after pigeon_channel_init copies them.
- **Verification:** Before: grep the free paths — cwire/session.go:83 and :207 call C.free with no preceding memzero. After: assert every channel/session free path invokes sodium_memzero on the key bytes first (code inspection; optionally an ASan/valgrind or a manual heap-inspection harness confirming the 32-byte key pattern is gone from the freed region).

### F16 — [LOW] streamTracker.streams grows without bound for the life of a single bridge (finished sub-streams never pruned)

- **Location:** `session.go:285`
- **Dimension:** -
- **Invariant violated:** Per-connection memory must be proportional to concurrently-live sub-streams, not to the cumulative number of sub-streams ever opened.
- **Failure scenario:** In bridge(), every accepted sub-stream pair is appended to tracker via tracker.add(src)/tracker.add(dst) (session.go:221-222, 246-247). bridgeStream closes the underlying QUIC streams on return (session.go:301-302), freeing quic-go state, but streamTracker.add only ever appends (session.go:283-287) and closeAll only runs once at bridge teardown (session.go:270); there is no per-stream removal. A client that serially opens, uses, and closes sub-streams in a loop over a long-lived bridge (staying within QUIC's max-concurrent-streams so each open succeeds) makes the relay retain one readWriteCloserPair interface value per stream forever. Over a multi-hour session with high stream churn the slice grows unboundedly (~tens of bytes per stream), a slow memory leak per bridged session that a hostile client can drive deliberately.
- **Evidence:**

```
func (t *streamTracker) add(s readWriteCloserPair) {
	t.mu.Lock()
	t.streams = append(t.streams, s)
	t.mu.Unlock()
}
// no corresponding remove(); bridgeStream closes streams but never deregisters them
```

- **Fix sketch:** Give streamTracker a remove(s) (e.g. back it with a map[readWriteCloserPair]struct{}) and have each bridgeStream pair deregister its two streams when it returns, so the tracker only holds currently-live streams. closeAll still closes whatever remains at teardown.
- **Verification:** Add a test that bridges two in-memory relaySessions, opens+closes K=10000 sub-streams serially, and asserts len(tracker.streams) stays O(concurrent) rather than O(K). Before fix the slice length equals ~2K.
